The specification

How does this differ from semver.org?

Semantic Versions is a spiritual successor to Semantic Versioning 2.0.0-rc.1, the draft that introduced optional pre-release and build versions. The next draft, 2.0.0-rc.2, turned builds into inert “build metadata,” which made them semantically useless. Semantic Versions reverts that change, so builds participate in precedence again, and adds the definitions tools were already relying on without a spec: sets, ranges, operators and comparators.

Anything valid under Semantic Versioning 2.0.0 is valid here and parses identically. The topic-by-topic comparison is on the proposal page, and the history traces how builds lost their meaning.

Why MUST minor and patch reset to 0?

Resetting keeps versions a single, well-defined total order and gives every line an unambiguous first member: 2.5.0 is the start of the 2.5 series, and 2.0.0 is the start of the 2.x series. Tools that reason about “the first release of a minor” or that desugar ranges (~, ^, ~>) rely on this. A carried-forward counter like 2.5.1 with no 2.5.0 breaks that assumption.

The rule constrains carrying a lower-position counter forward, not skipping numbers. You MAY skip values: 2.4.10 → 2.6.0 → 4.0.0 is fine, because each increment still starts its lower positions at 0. What the rule forbids is 2.4.10 → 2.5.1: the minor incremented, so patch MUST restart at 0.

This is also why Semantic Versions keeps MUST rather than relaxing it to SHOULD (as proposed in semver/semver#393). A normative relaxation would fragment the ordering guarantees that existing Semantic Versioning 2.0.0 tooling depends on, for a gain you can already have by skipping the numbers you don't want.

Why keep MAJOR.MINOR.PATCH instead of renaming to BREAKING.FEATURE.FIX?

Backward compatibility is the whole pitch. Anything valid under Semantic Versioning 2.0.0 stays valid here, and MAJOR.MINOR.PATCH is the vocabulary the ecosystem already speaks: parsers, registries, changelog tools and a decade of habit. Renaming the positions would fragment all of that for a purely cosmetic gain, so the names stay.

The confusion the renaming proposals react to is real, though, and worth stating plainly: an increment reflects the nature of the change to your public API (incompatible, additive, or a fix), not the amount of code that changed. A complete internal rewrite that leaves the public API untouched is still a patch; a one-character change that removes a parameter is a major bump. The number you increment is decided by what the change does to the contract, never by how much work it was.

To keep that meaning attached to the familiar labels, the spec states the intent next to each name: MAJOR is an incompatible change, MINOR an additive change, PATCH a fix. And a patch is exactly that, a fix, not a promise of backward compatibility (nothing can truly guarantee that).

What counts as the “public API”, and is Semantic Versions for apps and products?

“Public API” is meant broadly: it is whatever public interface or contract you declare. That might be a library's function signatures, a CLI's flags and output, a GUI's documented behaviour, a wire protocol or a file format. The spec does not care which kind of interface it is; it only requires that you declare one and increment based on changes to it. If your software's contract is its command-line surface, that surface is your public API for versioning purposes.

What a version is about is named by its context: source:name@version (for example npm:react@18.2.0) identifies a specific artifact in a specific ecosystem, the thing whose interface you are versioning, rather than leaving a bare 1.2.3 to mean whatever the reader assumes.

Because of that, Semantic Versions targets a declared interface, not a product's marketing, feature set or billing cadence. A “product version” that jumps to 2.0.0 for a licensing change, or that must land features on a planned 1.5.0, follows a different scheme, one where the number communicates roadmap or pricing rather than interface compatibility. That is a legitimate thing to want, but it is not what a semantic version measures. If you need both, version the declared interface semantically and give the product its own separate label.

What does the spec mean by “deprecated”?

Deprecation is a documentation and registry concern, not version syntax. The spec references it once (a minor MUST be incremented when public API functionality is marked as deprecated) and deliberately defines no notation for it. None is planned.

The reason is that deprecation is retroactive while a version string is not. You deprecate 1.2.3 after publishing it, often long after, and registries model this as mutable metadata attached to an already-published version. But the contents of a released version MUST NOT be modified, and its version string is fixed at publish time. There is no moment at which the string could be rewritten to record a decision made later.

Encoding it anyway would break precedence in both available slots. A pre-release lowers precedence and announces instability, which is not what a deprecation says: a deprecated release is usually stable, just unwanted. A build is worse. Because a build participates in precedence here, 1.2.3+deprecated would sort above 1.2.3 and be preferred by every range that matched it. The deprecated release would win, which is precisely backwards.

So mark deprecations in your documentation and in your registry's metadata, and ship the announcement in a minor release. A version number records what changed in the declared interface; it does not carry advice about whether to use a release. That advice is real and worth publishing; it simply belongs somewhere mutable.

Ecosystem

How does this relate to Package-URL (purl)?

They solve different problems and compose cleanly. Package-URL (ECMA-427) is an identifier: pkg:npm/react@18.2.0 standardises how to name and locate a package across ecosystems, and is what SBOMs (CycloneDX, SPDX) and vulnerability databases (OSV, CVE) reference. It deliberately says nothing about version semantics (precedence, ordering or matching) and defers ranges to its separate vers constraint syntax.

Semantic Versions is the complementary layer: it defines what a version means, covering precedence (including build), sets, ranges and comparators. A purl says which package; Semantic Versions says how its versions order and match. The source-qualified identity used here maps onto a purl one-to-one across every ecosystem (see the mapping table under Context), so a tool can carry both. The one thing neither purl qualifiers nor vers model is a precedence-bearing build, which is precisely the slot the extensions occupy.

The project

Where is the grammar?

Backus–Naur forms for versions, ranges and comparators are published on the grammar page, alongside the reference parser, semantic-versions. You can also try ranges against it in your browser.

Can I contribute, or propose an extension?

Yes. The specification, reference parser and extensions are developed in the open at vltpkg/semantic-versions. Open an issue or discussion to propose a change, report a defect, or float a new extension. Anything that rides on a source-qualified version and restored build precedence is in scope.
